# Сервер телеметрии для моделей (MCP) — эксплуатация и подключение

Проект и решения владельца — `docs/plans/design_mcp_telemetry.md` (Р0–Р16). Здесь —
как поставить, настроить и подключить. Версия cg-analytics 5.2.0 (этап Э1).

## Что это

Отдельный процесс рядом с cg-analytics: `python -m telemetry_mcp`, юнит
`cg-telemetry-mcp`. Протокол MCP (streamable HTTP, по умолчанию
`http://<сервер аналитики>:8095/mcp`). Только чтение; единственная запись — журнал
вызовов `mcp_calls` в БД аналитики. Про модели сервер не знает: хост цикла
(Claude Code, цикл cg-analytics, шлюз «Горыныч») подключается к нему как к набору
инструментов и сам решает, кого спрашивать.

Двенадцать инструментов в языке проекта: `equipment_tree`, `register_catalog`,
`series`, `state_at`, `timeline`, `segments`, `segment_report`, `episodes`,
`incident_acts`, `trend`, `kb_passport`, `fault_code`. Каждый ответ начинается
конвертом `[Tn]`: установка, окно, слой-источник, что отброшено защитой меток,
разрывы связи в окне, усечение, примечания.

## Установка на сервере аналитики

1. Обновить код и зависимости (в `requirements.txt` добавлен `mcp>=2.0,<3`; нужен
   Python ≥ 3.10):
   ```bash
   cd /opt/cg-analytics && git pull && .venv/bin/pip install -r requirements.txt
   ```
2. Перезапустить cg-analytics — при старте он играет `db/online_schema.sql` и создаёт
   таблицы `units`, `unit_sensors`, `mcp_calls` и колонку `online_observations.unit_id`
   (только расширяющая миграция, без CHECK):
   ```bash
   sudo systemctl restart cg-analytics
   ```
3. Поставить и запустить юнит сервера телеметрии:
   ```bash
   sudo cp /opt/cg-analytics/cg-telemetry-mcp.service /etc/systemd/system/
   sudo systemctl daemon-reload && sudo systemctl enable --now cg-telemetry-mcp
   ```
4. Проверить:
   ```bash
   curl -s http://127.0.0.1:8095/health
   ```
   Ответ — `{"status":"ok","tools":[…12 имён…]}`. Журнал процесса:
   `journalctl -u cg-telemetry-mcp -f`.

Сетевой доступ — как у шлюза и Библиотекаря: локальная сеть и офисный туннель
(ufw: порт 8095 для 192.168.0.0/24 и 10.5.5.0/24). Ключа нет; источник вызова
передаётся заголовком `X-Source` и ограничивается списком `sources` в конфиге.

## Конфигурация

Секция `telemetry_mcp` в `config.yml` (образец — `config.example.yml`): адрес и порт,
типы панелей (`panel_types`, по умолчанию `[pcc]`), разрешённые инструменты по
источнику, лимиты сервера (окно сырого ряда 48 ч, 150 точек, 8 параметров, лента
300 строк, результат ~8 тыс. токенов, вызов 20 с), журнал. Лимиты — сервисные
настройки, не KB (решение Р12); пересматриваются по журналу `mcp_calls`.

## Карта установок

Иерархия владельца: объект (роутер) → установка → панель + датчики. Карта живёт
в аналитике (Р7): таблицы `units` и `unit_sensors`, карточка «Установки» в
настройках cg-analytics, дерево — `GET /api/units` (его же читает UI-telemetry).
Пока владелец не привязал датчики руками, действует правило: датчик того же
роутера с тем же номером панели принадлежит этой панели; непривязанные видны под
объектом как «не привязаны». Привязка KB остаётся у панели в реестре оборудования.
Кнопка «Завести по реестру» (или первый старт сервера телеметрии) создаёт строки
установок для всех панелей реестра — у каждой появляется постоянный id.

## Подключение Claude Code (Э1, интерактив)

С рабочей машины инженера:
```bash
claude mcp add --transport http cg-telemetry http://192.168.0.194:8095/mcp --header "X-Source: claude-code"
```
Дальше в диалоге: «посмотри equipment_tree», «что было с ДЭС №3 13.10 с 12:00 до 13:30»
— Claude Code сам вызывает инструменты. Приёмка Э1 — три эталонных вопроса из
проекта (Сининда 29.09, ДЭС №3 13.10, ДГУ №1 16.10), в ответах есть блок «## Данные».

Сквозной идентификатор задачи хост передаёт либо в `_meta.task_id` вызова, либо
заголовком `X-Task-Id` — он попадает в `mcp_calls.task_id` и в метки `[Tn]`.

## Журнал и проверка после деплоя

- `mcp_calls`: инструмент, установка, аргументы, окно, строки, байты, усечение,
  отброшенные строки, длительность, статус. Запрос для сводки по инструментам:
  ```sql
  SELECT tool, count(*), avg(duration_ms)::int AS ms, avg(bytes)::int AS bytes,
         sum((status<>'ok')::int) AS errors
  FROM mcp_calls WHERE ts > now() - interval '7 days' GROUP BY tool ORDER BY 2 DESC;
  ```
- Тесты чистых функций: `.venv/bin/python scripts/test_mcp_e1.py`.
- Проверка живьём без Claude Code: `.venv/bin/python scripts/mcp_probe.py --unit "ДЭС №3"`
  (список инструментов, дерево, лента и ряд за последний час).

## Полировка v5.2.3 по замечаниям приёмки (02.11.2026)

- Имена параметров разбираются по основам слов и каталогу: «ток нейтрали» → регистр
  40030 «Ток в нейтральном проводнике генератора» (вне KB, но в каталоге).
- `series` на окнах длиннее 48 ч считается на стороне БД по корзинам `time_bucket`
  (минимум, максимум, среднее по времени удержания); защита меток там — только от
  меток в будущем, о чём говорит конверт. Сводка печатается перед таблицей, чтобы при
  усечении по размеру терялись строки, а не итоги.
- `trend` для регистров вне KB (нет роли) берёт сутки из часовых агрегатов
  телеметрии с пометкой «среднее по отсчётам».
- `timeline` и `state_at` сообщают, если окно или момент старше срока хранения
  истории; события и разрывы, начавшиеся до окна или в другие сутки, печатаются с датой.
- `segment_report` называет запрошенные, но отсутствующие разделы.
- Заключения совета в `incident_acts` помечены как текст модели со временем,
  возможно, в UTC.
- Метка `[Tn]` присваивается только состоявшемуся ответу: ошибка номер не съедает.
- Новый ключ `telemetry_mcp.source_db` — своя БД телеметрии для сервера. Реплика в БД
  аналитики (`databases.analytics`) хранит историю без обрезки (с мая 2026), тогда как
  источник режет её через 30 дней; на реплике нет TimescaleDB и `history_1hour`, поэтому
  запасной путь `trend` для регистров вне KB там отвечает пометкой. Решение, куда
  смотреть серверу, — за владельцем при деплое.

## Состояние Э1 и отклонения от проекта (01.11.2026)

Реализовано на ветке `claude/mcp-e1` (v5.2.0), проверено с рабочей машины против
БД телеметрии (.130) и аналитики (.194) по трём эталонам проекта: ДЭС №3 13.10 (лента,
ряд, снимок, сегменты), ДГУ №1 16.10 (акты, эпизоды, ряд с соседом, тренд, коды),
Сининда 29.09 — только аналитика (сегменты, эпизоды): **история телеметрии в
источнике хранится 30 дней** (retention TimescaleDB, записи с 01.10), сырых рядов за
29.09 уже нет; сервер пишет об этом в конверте и отсылает к `segments`, `episodes`,
`incident_acts`, `trend`.

Отклонения от текста `design_mcp_telemetry.md`, сверить при приёмке:
- `units.kb_profile` не заведён: привязка KB остаётся у панели в `equipment_registry`.
- Роль сервера в БД аналитики не «только чтение»: запись в `mcp_calls` (журнал) и в
  `units` при материализации умолчаний. К реплике телеметрии — только SELECT.
- Пока таблицы карты не созданы (cg-analytics не перезапущен), карта работает по
  правилу умолчания, установки без id — обращение по имени.
- `kb_passport` ищет и в `detectors.yaml` (несимметрия, нейтраль — с norm_ref):
  в `thresholds.yaml` разделов по токам нет.
- Приёмка «из Claude Code» ждёт деплоя и `claude mcp add`; пробы выполнены
  MCP-клиентом `scripts/mcp_probe.py`.

## Что намеренно не делается

Запись в телеметрию или аналитику через инструменты; произвольный SQL; поиск
похожих случаев по корпусу (отложен); перенос Библиотекаря на MCP; уровень
«объект» в KB.

# Сервер телеметрии для моделей (MCP) — эксплуатация и подключение

Проект и решения владельца — `docs/plans/design_mcp_telemetry.md` (Р0–Р16). Здесь —
как поставить, настроить и подключить. Версия cg-analytics 5.2.0 (этап Э1).

## Что это

Отдельный процесс рядом с cg-analytics: `python -m telemetry_mcp`, юнит
`cg-telemetry-mcp`. Протокол MCP (streamable HTTP, по умолчанию
`http://<сервер аналитики>:8095/mcp`). Только чтение; единственная запись — журнал
вызовов `mcp_calls` в БД аналитики. Про модели сервер не знает: хост цикла
(Claude Code, цикл cg-analytics, шлюз «Горыныч») подключается к нему как к набору
инструментов и сам решает, кого спрашивать.

Тринадцать инструментов в языке проекта (двенадцать из Э1 и `chart` с v5.2.5): `equipment_tree`, `register_catalog`,
`series`, `state_at`, `timeline`, `segments`, `segment_report`, `episodes`,
`incident_acts`, `trend`, `kb_passport`, `fault_code`. Каждый ответ начинается
конвертом `[Tn]`: установка, окно, слой-источник, что отброшено защитой меток,
разрывы связи в окне, усечение, примечания.

## Установка на сервере аналитики

1. Обновить код и зависимости (в `requirements.txt` добавлен `mcp>=2.0,<3`; нужен
   Python ≥ 3.10):
   ```bash
   cd /opt/cg-analytics && git pull && .venv/bin/pip install -r requirements.txt
   ```
2. Перезапустить cg-analytics — при старте он играет `db/online_schema.sql` и создаёт
   таблицы `units`, `unit_sensors`, `mcp_calls` и колонку `online_observations.unit_id`
   (только расширяющая миграция, без CHECK):
   ```bash
   sudo systemctl restart cg-analytics
   ```
3. Поставить и запустить юнит сервера телеметрии:
   ```bash
   sudo cp /opt/cg-analytics/cg-telemetry-mcp.service /etc/systemd/system/
   sudo systemctl daemon-reload && sudo systemctl enable --now cg-telemetry-mcp
   ```
4. Проверить:
   ```bash
   curl -s http://127.0.0.1:8095/health
   ```
   Ответ — `{"status":"ok","tools":[…13 имён…]}`. Журнал процесса:
   `journalctl -u cg-telemetry-mcp -f`.

Сетевой доступ — как у шлюза и Библиотекаря: локальная сеть и офисный туннель
(ufw: порт 8095 для 192.168.0.0/24 и 10.5.5.0/24). Ключа нет; источник вызова
передаётся заголовком `X-Source` и ограничивается списком `sources` в конфиге.

## Конфигурация

Секция `telemetry_mcp` в `config.yml` (образец — `config.example.yml`): адрес и порт,
типы панелей (`panel_types`, по умолчанию `[pcc]`), разрешённые инструменты по
источнику, лимиты сервера (окно сырого ряда 48 ч, 150 точек, 8 параметров, лента
300 строк, результат ~8 тыс. токенов, вызов 20 с), журнал. Лимиты — сервисные
настройки, не KB (решение Р12); пересматриваются по журналу `mcp_calls`.

## Карта установок

Иерархия владельца: объект (роутер) → установка → панель + датчики. Карта живёт
в аналитике (Р7): таблицы `units` и `unit_sensors`, карточка «Установки» в
настройках cg-analytics, дерево — `GET /api/units` (его же читает UI-telemetry).
Пока владелец не привязал датчики руками, действует правило: датчик того же
роутера с тем же номером панели принадлежит этой панели; непривязанные видны под
объектом как «не привязаны». Привязка KB остаётся у панели в реестре оборудования.
Кнопка «Завести по реестру» (или первый старт сервера телеметрии) создаёт строки
установок для всех панелей реестра — у каждой появляется постоянный id.

## Подключение Claude Code (Э1, интерактив)

С рабочей машины инженера:
```bash
claude mcp add --transport http cg-telemetry http://192.168.0.194:8095/mcp --header "X-Source: claude-code"
```
Дальше в диалоге: «посмотри equipment_tree», «что было с ДЭС №3 13.10 с 12:00 до 13:30»
— Claude Code сам вызывает инструменты. Приёмка Э1 — три эталонных вопроса из
проекта (Сининда 29.09, ДЭС №3 13.10, ДГУ №1 16.10), в ответах есть блок «## Данные».

Сквозной идентификатор задачи хост передаёт либо в `_meta.task_id` вызова, либо
заголовком `X-Task-Id` — он попадает в `mcp_calls.task_id` и в метки `[Tn]`.

## Журнал и проверка после деплоя

- `mcp_calls`: инструмент, установка, аргументы, окно, строки, байты, усечение,
  отброшенные строки, длительность, статус. Запрос для сводки по инструментам:
  ```sql
  SELECT tool, count(*), avg(duration_ms)::int AS ms, avg(bytes)::int AS bytes,
         sum((status<>'ok')::int) AS errors
  FROM mcp_calls WHERE ts > now() - interval '7 days' GROUP BY tool ORDER BY 2 DESC;
  ```
- Тесты чистых функций: `.venv/bin/python scripts/test_mcp_e1.py`.
- Проверка живьём без Claude Code: `.venv/bin/python scripts/mcp_probe.py --unit "ДЭС №3"`
  (список инструментов, дерево, лента и ряд за последний час).

## Хост цикла в cg-analytics (этап Э2б)

Сервис сам может быть хостом инструментов: разбор аварии на облаке идёт циклом «вопрос → вызов инструмента → ответ» (`llm/agent_loop.py`), инструменты исполняет этот сервер.

- **Где включается.** Настройки → «Кто и как разбирает», строка «Разбор аварии»: «Кто» — Claude API, затем подключение из реестра (Claude, OpenAI, DeepSeek, Gemini; пусто — Claude с ключом config.yml), флажок «Инструменты телеметрии» и три поля бюджета (вызовы, токены контекста, минуты; пусто — умолчание). Рядом с флажком — состояние сервера со стороны хоста (`GET /api/telemetry-mcp/status`).
- **Провайдеры цикла.** Claude — официальный SDK; OpenAI — Responses API (новые модели не принимают инструменты с рассуждением через chat/completions); DeepSeek и Gemini — chat/completions (у Gemini точка OpenAI-формата Google); шлюз «Горыныч» — прямой режим. Приёмка 13.11.2026 — девять прогонов, отчёт `docs/plans/acceptance_mcp_e2b_2026-11-13.md`.
- **Адрес сервера для хоста** — `telemetry_mcp.client_url` в config.yml (умолчание `http://127.0.0.1:<port><path>`); умолчания бюджетов — `telemetry_mcp.host_budgets`.
- **Что получает модель.** Бриф прежний (акт, ход цикла, картина объекта, отчёт сегмента); к системному промпту добавляются правила для инструментов (набор `TOOL_RULES`, отметка «+tN» в версии промпта; с v5.2.11 — «+t2»); модели без признака «зрение» инструмент `chart` не предлагается.
- **Что в результате.** Текст разбора, блок «## Данные» (его собирает хост из первых строк ответов инструментов: метка [Tn], установка, инструмент, окно) и подпись: модель, число вызовов инструментов, объём контекста, стоимость, причина остановки по пределу. Сводка прогона — в записи разбора (`warning_analyses.extra.loop`).
- **Журналы.** Каждый шаг цикла — строка `llm_calls` (номер прогона `run_id`, итерация, токены, стоимость, размер результатов инструментов); вызовы инструментов — `mcp_calls` с тем же номером в `task_id`. Один прогон восстанавливается по двум журналам.
- **Отказы.** Сервер недоступен на входе — разбор одним запросом без инструментов, в подписи «инструменты недоступны». Три сбоя сети подряд — инструменты до конца прогона не исполняются. Предел бюджета — модель получает пометку «отвечай по собранному»; список инструментов в запросе при этом не меняется.
- **Что не уходит в облако.** Серийный номер роутера вычищается из брифа на облачном пути (он стоит в заголовке отчёта сегмента); ответы инструментов серийников не содержат.
- **Приёмка вне сервиса:** `python scripts/incident_tools_probe.py --act <id сегмента с актом> [--entry <id записи реестра>] --mcp-url http://<сервер>:8095/mcp --out exports/e2b` — в БД ничего не пишет. Ключи провайдеров для таких прогонов — локальным файлом (`--keys-file`, проверка `--check-keys`), цены для стоимости — `--prices`.

## Пометки базы знаний к регистрам (v5.2.13, 14.11.2026)

Решение владельца 14.11.2026 (`docs/plans/design_kb_register_notes.md`). Имя и единица регистра не говорят, из чего складывается его значение и чем оно ограничено. Это знание об оборудовании лежит в базе знаний и доходит до модели через инструменты.

- **Поля записи регистра** в `knowledge_base/…/analytics/mapping.yaml`: `note_ru` — текст для модели, `note_source` — документ, раздел, страница. В тексте только то, что написано в источнике. В слое контроллера — ничего про конкретные установки и случаи: слой общий для всех машин с этим контроллером. Движок аналитики эти поля не читает.
- **Без источника пометка не показывается:** сервер ведёт себя так, будто её нет, и пишет в журнал одно предупреждение на адрес.
- **`register_catalog`:** в списке до 10 регистров (поиск по слову или адресу) под строкой регистра идут две строки — «пометка: …» и «источник: …». В длинном списке текста нет, в примечаниях конверта — «есть пометка базы знаний у регистров: …».
- **`kb_passport`:** с параметром — блок «[регистр N · имя]» с пометкой и источником после разделов порогов; у параметра без раздела порогов пометка идёт ответом вместо отказа. Без параметра — все пометки базы знаний.
- **Первая пометка — регистр 40595 «Задание частоты (регулятор)»:** состав задания (базовая частота, ручная подстройка, внешний вход смещения скорости, смещение параллельной работы), ограничение 60–110 % базовой частоты (30…55 Гц при 50 Гц), контуры параллельной работы, условие включения синхронизатора, регистры контура. Источник — сервисное руководство PowerCommand 3.3 (0900-0670), разд. 6.5.1 и 7.2–7.4.
- **Код:** `telemetry_mcp/kb_notes.py`; вызовы — в `build_catalog` и `kb_passport` (`telemetry_mcp/tools_equipment.py`).
- **Тесты:** `scripts/test_kb_notes_v5213.py` — в том числе правило «у каждой `note_ru` есть `note_source`».
- **Деплой:** перезапуск `cg-telemetry-mcp`. Сервер читает базу знаний сам, кэш конфига — 10 минут. Если у файла `mapping.yaml` есть рабочая копия в `knowledge_base_work/`, читается она, а не git: пометку нужно внести и туда.

## Перечень опрашиваемых регистров (v5.2.11, 14.11.2026)

Решение владельца 14.11.2026 (`docs/plans/design_tool_rules_v2.md`, разд. 7). В телеметрию попадают только регистры, опрос которых заложен в настройке роутера; опроса по требованию нет. В карте панели PCC 1353 регистра, на установку опрашивается 110–140. Сервер показывает модели, какие регистры доступны, и не отдаёт пустые ряды молча.

- **Откуда перечень.** Основной источник — таблица последних значений `latest_state` исходной БД (`databases.source`): строка на каждый регистр, который роутер хоть раз прислал. Сервер читает её отдельным коротким соединением, даже когда ряды берёт из реплики (`telemetry_mcp.source_db`). Запасной источник, когда исходная БД недоступна, — записи реплики (`history`, `enum_history`, `fault_history`); он неполон: регистр, который опрашивается, но ни разу не менялся, записей не имеет.
- **`register_catalog`** по умолчанию показывает только опрашиваемые регистры, в шапке — «Опрашивается регистров: N из M в карте панели». Колонка «опрос»: дата последней записи, «значение не менялось (v)» или «не опрашивается». Вся карта панели — `all_registers=true`. Если слово поиска есть только в карте панели, каталог говорит, что такие регистры есть, но не опрашиваются.
- **Краткий перечень (v5.2.12).** Без слова поиска `register_catalog` отдаёт перечень в кратком виде: маски неисправностей одной строкой (диапазоны адресов; какие ни разу не менялись; при `all_registers` — какие не опрашиваются), состояния не расшифровываются, а дата последней записи, общая для большинства строк, вынесена в шапку — в строке остаётся только то, что отличается. Полная строка регистра с состояниями, числом битов и датой — поиском по слову или адресу. Причина: перечень из 113–137 регистров не помещался в предел результата (`limits.result_max_tokens`, 8000) и обрезался по хвосту — у ДЭС №3 в ответе было 106 строк из 137, без задания частоты 40595. После правки: ДГУ — около 4,7 тыс. токенов, ДЭС №3 — около 5,9 тыс., все регистры на месте. Тесты: `scripts/test_catalog_compact_v5212.py`. Деплой: перезапуск `cg-telemetry-mcp`.
- **`series`, `chart`, `state_at`, `trend`** делят запрошенные параметры на опрашиваемые и нет: по вторым пишут «роутером не опрашивается, данных нет»; если не опрашивается ни один — ответ целиком об этом. По регистру без записей изменения — пометка «значение держится» с самим значением. У соседей по объекту перечень свой.
- **`equipment_tree`** дописывает к установке «опрашивается регистров: N из M».
- **Запасной режим говорит осторожнее:** «Регистров с записями…», «записей нет», «не опрашивается или его значение не менялось».
- **Кэш.** Перечень на установку держится `limits.availability_ttl_min` минут (умолчание 30); устаревший отдаётся сразу и обновляется в фоне; на старте сервера перечни всех установок прогреваются.
- **Принятое ограничение.** Регистр, снятый с опроса, остаётся в перечне: по `latest_state` его не отличить от регистра с неизменным значением.
- **Правила промпта для инструментов — версия 2** (отметка «+t2»): десять правил. Новые: R-T-AVAIL (запрашивать только регистры из перечня; чего недостаёт — сказать прямо), R-T-HISTORY (отказ на пуске сравнить с прошлыми пусками той же установки), R-T-SETPOINT (при раскачке сравнить задание регулятора с фактом); R-T-ONCE разрешает списки сегментов и актов за одну-две недели.
- **Проверка 14.11.2026** — акты #35941 и #35861 на Claude, OpenAI и Gemini против сервера с новым кодом (`exports/e2b_v2/`): запросов к неопрашиваемым регистрам 0, выгрузок всей карты панели 0; на #35941 все три модели нашли задание частоты запросом «задание» и сравнили с прошлыми пусками.
- **Тесты:** `scripts/test_mcp_avail_v5211.py`.
- **Деплой:** перезапуск `cg-telemetry-mcp` (новый код сервера) и `cg-analytics` (правила промпта). В журнале сервера после старта — строка о прогреве перечней.

## График и значение на входе окна (v5.2.5, этап Э2а, 12.11.2026)

- **Инструмент 13 `chart`** (решения Р17, Р21 в `docs/plans/design_mcp_e2.md`): аргументы как у
  `series` (параметров до 4, `with_neighbors`), ответ — картинка PNG 1200 px и та же числовая
  сводка. На картинке панель на параметр, общая ось времени в поясе сервиса, своя установка
  сплошной линией, соседи пунктиром, разрывы связи штриховкой, номинал точечной линией; линии
  ступенчатые (значение держится до следующей записи), при укрупнении — линия среднего по времени
  и полоса мин–макс. Правило для модели: форму смотреть на картинке, числа брать только из сводки.
  Сервер про модель не знает и отдаёт картинку всегда; моделям без зрения инструмент не предлагает
  хост цикла (Р21).
- **Значение на входе окна** у `series` и `chart`: если до окна есть запись не старше
  `series_seed_max_age_hours` (6 ч) и между ней и окном не было разрыва связи, оно держится с
  начала окна. Раньше ряд был пуст до первой записи в окне, хотя значение держалось. В сводку и
  счёт записей такое значение не входит; конверт об этом говорит.
- **Без структурного вывода**: у инструментов убрана схема `structuredContent` — SDK слал каждый
  текст дважды (в `content` и в `structuredContent.result`).
- **`/health`** отдаёт версию из файла `VERSION` (поле `package` — версия пакета).
- Новая зависимость `matplotlib` (рендер без GUI); при старте сервис в фоне прогревает рендер
  (кэш шрифтов), чтобы первый вызов не упёрся в срок.
- Лимиты в секции `telemetry_mcp.limits`: `chart_max_params` (4), `chart_max_points` (600),
  `series_seed_max_age_hours` (6).
- Тесты: `scripts/test_mcp_e2a.py`; проба сохраняет картинки:
  `scripts/mcp_probe.py --call chart --args '{…}' --save-images <папка>`.
- **Деплой**: `pip install -r requirements.txt` (matplotlib) и перезапуск юнита `cg-telemetry-mcp`;
  cg-analytics перезапускать не нужно.

## Полировка v5.2.3 по замечаниям приёмки (02.11.2026)

- Имена параметров разбираются по основам слов и каталогу: «ток нейтрали» → регистр
  40030 «Ток в нейтральном проводнике генератора» (вне KB, но в каталоге).
- `series` на окнах длиннее 48 ч считается на стороне БД по корзинам `time_bucket`
  (минимум, максимум, среднее по времени удержания); защита меток там — только от
  меток в будущем, о чём говорит конверт. Сводка печатается перед таблицей, чтобы при
  усечении по размеру терялись строки, а не итоги.
- `trend` для регистров вне KB (нет роли) берёт сутки из часовых агрегатов
  телеметрии с пометкой «среднее по отсчётам».
- `timeline` и `state_at` сообщают, если окно или момент старше срока хранения
  истории; события и разрывы, начавшиеся до окна или в другие сутки, печатаются с датой.
- `segment_report` называет запрошенные, но отсутствующие разделы.
- Заключения совета в `incident_acts` помечены как текст модели со временем,
  возможно, в UTC.
- Метка `[Tn]` присваивается только состоявшемуся ответу: ошибка номер не съедает.
- Новый ключ `telemetry_mcp.source_db` — своя БД телеметрии для сервера. Реплика в БД
  аналитики (`databases.analytics`) хранит историю без обрезки (с мая 2026), тогда как
  источник режет её через 30 дней; на реплике нет TimescaleDB и `history_1hour`, поэтому
  запасной путь `trend` для регистров вне KB там отвечает пометкой. Решение, куда
  смотреть серверу, — за владельцем при деплое.

## Состояние Э1 и отклонения от проекта (01.11.2026)

Реализовано на ветке `claude/mcp-e1` (v5.2.0), проверено с рабочей машины против
БД телеметрии (.130) и аналитики (.194) по трём эталонам проекта: ДЭС №3 13.10 (лента,
ряд, снимок, сегменты), ДГУ №1 16.10 (акты, эпизоды, ряд с соседом, тренд, коды),
Сининда 29.09 — только аналитика (сегменты, эпизоды): **история телеметрии в
источнике хранится 30 дней** (retention TimescaleDB, записи с 01.10), сырых рядов за
29.09 уже нет; сервер пишет об этом в конверте и отсылает к `segments`, `episodes`,
`incident_acts`, `trend`.

Отклонения от текста `design_mcp_telemetry.md`, сверить при приёмке:
- `units.kb_profile` не заведён: привязка KB остаётся у панели в `equipment_registry`.
- Роль сервера в БД аналитики не «только чтение»: запись в `mcp_calls` (журнал) и в
  `units` при материализации умолчаний. К реплике телеметрии — только SELECT.
- Пока таблицы карты не созданы (cg-analytics не перезапущен), карта работает по
  правилу умолчания, установки без id — обращение по имени.
- `kb_passport` ищет и в `detectors.yaml` (несимметрия, нейтраль — с norm_ref):
  в `thresholds.yaml` разделов по токам нет.
- Приёмка «из Claude Code» ждёт деплоя и `claude mcp add`; пробы выполнены
  MCP-клиентом `scripts/mcp_probe.py`.

## Что намеренно не делается

«объект» в KB.
